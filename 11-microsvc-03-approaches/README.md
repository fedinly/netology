# Решение домашнего задания к занятию «Микросервисы: подходы»
## Задача 1.
- Для обеспечения разработки можно предложить решение для обеспечения процесса разработки на основе Amazon Web Services:
  1) Облачная платформа, возможно внедрение Serverless-подхода с использованием продукта AWS Lambda;
  2) Центральное место для хранения всего кода команды с применением AWS CodeCommit;
  3) Репозитории образов контейнеров с Amazon ECR;
  4) Решение для сервиса сборки CI/CD: AWS CodePipeline, которое поддерживает параметризованные пайплайны для реализации запуска «по кнопке» с вводом параметров и через механизм триггеров (Triggers) и CodeStarSourceConnection
     (для запуска сборки по событию из AWS CodeCommit);
  5) В AWS CodePipeline создание шаблонов сборки и конвейеров реализовано через концепцию конвейера как кода (Pipeline as Code);
  6) Решение для хранения секретов - AWS Secrets Manager;
  7) Для запуска нескольких сборок (конфигураций) из одного репозитория (в монорепозитории), используют параллельные шаги CodeBuild;
  8)  В настройках источника  для разных конвейеров в AWS CodePipeline можно задать фильтрацию пути к файлам/папкам (Folder paths) или триггеры на разные ветки (например, dev, feature) , чтобы изменения запускали только нужную конфигурацию;
  9)  В AWS CodeBuild можно использовать собственные (кастомные) Docker-образы для сборки проектов; образ загружается в ⁠Amazon ECR;
  10) Можно развернуть агенты сборки GitLab Runner или GitHub Actions на своих серверах, далее агенты будут собирать код например в AWS Lambda;
  11) В AWS используются сервисы ⁠CodeBuild (включая пакетные сборки ⁠Batch Builds и параллельное разделение тестов ⁠Parallel test execution);
-  Amazon предлагает всю линейку продуктов в одном портале; процессы интегрируются в пайплайны  для проверки качества на каждом этапе разработки (Непрерывное тестирование). Также есть возможность эмуляции пользователей, тесты можно запускать из различных географических регионов для точной имитации условий.
Таже есть возможность запускать процессы разработки, сборки, тестирования на нескольких площадках, включая Azure и Google Cloud.
## Задача 2.
- Сбор логов сервисов можно осуществлять в ⁠Amazon CloudWatch Logs (с помощью агента или плагина) с последующим анализом. 
  1) Сбор логов из stdout возможно, если развернуть ⁠Fluent Bit DaemonSet или CloudWatch Agent, которые будут перехватывать логи уровня ноды/контейнеров;
  2) Централизация встроена в CloudWatch;
  3) Доставка логов до центрального хранилища не гарантируется по причине особенности в технологии Batching. При переполнении буфера или сетевых задержках логи могут быть потеряны;
  4) Поиск в логах осуществляется базовым поиском по шаблонам (Filter Patterns) или инструментом CloudWatch Logs Insights с использованием конвейерных запросов;
  5) ⁠Amazon CloudWatch Logs панель предоставляет возможность работать с группами журналов, аналитикой журналов, панелями мониторинга, метрическими фильтрами;
  6) Перейти по ссылке на запись можно в единой консоли Log Analytics или классический раздел Logs Insights ⁠на странице консоли AWS.
## Задача 3.
- Сбор и анализ состояния хостов и сервисов в микросервисной архитектуре AWS реализуется через ⁠AWS Native Services (CloudWatch, X-Ray) или стек Open-Source (Prometheus, Grafana),
  1) Для централизованного сбора метрик используется ⁠Amazon CloudWatch. Для этого на каждый хост устанавливается ⁠агент CloudWatch (или сборщик OpenTelemetry), системные метрики (CPU, память, диск) отправляются в хранилище ⁠CloudWatch;
  2) Для мониторинга микросервисов по отдельности используется тегирование инстансов/контейнеров и ⁠агент CloudWatch или настройка OpenTelemetry с разделением пространств имен;
  3) Если микросервис пишет логи определенного формата, в ⁠консоли CloudWatch настраиваются фильтры (Metric Filters); либо если микросервис отдает лог в формате EMF (JSON) в stdout, локальный агент перехватывает их и отправляет в ⁠CloudWatch Metrics;
  4) CloudWatch Logs Insights - сервис в консоли AWS, позволяющий выполнять поисковые запросы, фильтрацию и агрегацию логов с использованием специального синтаксиса;
  5) Там же можно настроить дашборды для каждого микросервиса.
 
Если существует опасение, что вследствие санкционных ограничений возможна потеря доступа к данным или самих данных и сервисов (вследствие отключения площадки AWS в РФ), можно рассмотреть возможность создания площадки разработки и деплоя на платформе Yandex Cloud.  
- Доступна аренда виртуальных машин через ⁠Yandex Compute Cloud, ВМ  масштабируются под микросервисы;
- Создание репозиториев для хранения и использования артефактов с помощью ⁠Yandex Cloud Registry;
- При необходимости запускать и тестировать код без управления серверами можно с помощью Yandex Cloud Functions;
- Защищенное хранение секретов в Yandex Lockbox;
- Управление инфраструктурой посредством открытого задокументированного API;
- Доступкен мониторинг производительности и визуализация с помощью Yandex Monitoring;
- Чтение и агрегация логов с помощью Yandex Cloud Logging;
- Доступен сервисч обмена сообщениями между микросервисами Yandex Managed Service for Apache Kafka;
- Возможно, сервис сборки и развертывания с заявленными требованиями придется развернуть самостоятельно (на основе Jenkins, TeamCity).
